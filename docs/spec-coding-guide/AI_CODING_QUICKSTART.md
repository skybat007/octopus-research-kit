# AI Collaboration Guide

本文面向开发人员, 说明如何通过 AI 协作完成 Spec Coding 和开发实现。

Spec Coding 不要求开发人员手写大量文档。开发人员的核心职责是提供关键信息、确认范围和做决策; AI 负责整理、生成、对齐、实现和回填。

如果只想快速开始, 可直接阅读第 3 节“推荐协作流程”和第 5 节“常用提示”。

## 1. 规范目的

这套 Spec Coding 规范的目的，不是要求开发人员手写大量文档，也不是把开发流程变得更重，而是为了让 AI、开发人员和协作团队在复杂需求开发中形成可追溯、可确认、可继承、可执行的协作方式。

在实际项目中，AI 很擅长整理材料、补全文档、生成设计和实现代码，但也容易出现以下问题：

- 把模糊需求理解成确定需求
- 把合理猜测写成已确认结论
- 因为“最佳实践”而擅自扩大范围
- 在需求、设计、任务和代码之间产生不一致
- 忽略项目已有架构、术语和系统边界
- 顺手实现本期并不需要的功能
- 多人协作时，需求背景、设计决策和任务进展分散在聊天记录、会议纪要或个人理解中
- 切换不同 AI 模型或 Code Agent 后，因为上下文不一致，导致设计方向、实现方式和任务拆解发生偏移

因此，本规范的核心目标是：

### 1.1 把原始材料变成可确认的 Spec

开发人员可以直接输入产品文档、会议纪要、截图、口头想法或技术设想，由 AI 先整理成需求、设计、任务和验收标准，再由开发人员确认关键边界。

Spec 的价值不是一次性写出完美文档，而是先形成一份可讨论、可修改、可确认的上下文基线。

---

### 1.2 让 AI 的推测和建议显式暴露

AI 可以挖掘隐含需求、提出架构建议、补充异常场景，但必须区分：

- 已确认范围
- 架构必要约束
- 建议纳入本期
- 待确认问题
- 后续演进
- 不做范围

未经确认的内容，不得直接进入本期任务，不得直接进入 Coding。

---

### 1.3 用 Spec 约束 Coding 行为

AI 进入编码前必须知道当前任务对应的需求、设计和验收标准。

没有进入 Spec 的内容，不应直接编码。

Spec 是 Coding 的输入契约，不只是参考材料。

---

### 1.4 降低复杂需求中的范围漂移

对涉及多系统、多角色、多接口、状态流转、权限、异步任务的需求，必须通过 Spec 明确边界，避免 AI 或开发人员在实现过程中不断扩展范围。

尤其是当需求从“产品想法”进入“技术实现”时，必须明确：

- 本期做什么
- 本期不做什么
- 哪些是架构必要约束
- 哪些只是后续演进方向

---

### 1.5 建立项目级长期记忆

Spec 是项目的长期记忆，不应该只存在于一次 AI 对话、一次会议纪要或某个人的脑子里。

通过 Spec，可以长期沉淀：

- 需求背景
- 业务目标
- 系统参与者
- 设计决策
- 接口约定
- 数据结构
- 状态流转
- 任务拆解
- 验收标准
- 已确认问题
- 待确认问题
- 后续演进方向
- 当前任务进展

这样在多人协作时，新加入的开发人员、测试人员、产品人员或 AI Agent，都可以快速了解当前需求的背景、边界、设计和进展。

---

### 1.6 支撑多人协同和任务交接

在多人协作中，Spec 应作为需求和任务进展的共同基准。

它可以帮助团队快速回答：

- 当前需求为什么要做？
- 本期到底做哪些内容？
- 哪些内容明确不做？
- 技术方案为什么这样设计？
- 哪些任务已经完成？
- 哪些任务还在进行？
- 哪些问题还没有确认？
- 当前代码实现是否偏离原始设计？
- 测试应该按什么标准验收？

Spec 的作用不是替代沟通，而是降低重复沟通成本，减少因个人理解不同导致的偏差。

---

### 1.7 支撑不同模型和不同 Code Agent 之间的上下文一致性

Spec 也是跨模型、跨 Agent 协作的上下文锚点。

在实际开发中，团队可能会切换不同模型或工具，例如：

- Codex
- Cursor
- Claude Code
- GPT
- Qwen Coder
- Gemini CLI
- 其他内部 Code Agent

不同模型的推理风格、代码偏好、设计倾向可能不同。如果没有统一 Spec，不同模型可能会基于同一段需求生成完全不同的设计、任务拆解和实现方案。

通过 Spec，可以让不同模型都先读取同一份上下文基线，再进行设计、编码和测试。

这可以避免：

- A 模型按一种架构设计
- B 模型换了一套接口
- C 模型重新理解了需求边界
- D 模型把后续演进功能提前实现
- 不同 Agent 之间产生不兼容的代码和文档

因此，不管切换到哪个模型，都应优先读取当前需求目录下的 Spec，并以 Spec 作为需求、设计和任务协作的基准上下文。涉及实际行为时, 仍应对照当前代码实现。

---

### 1.8 建立需求、设计、任务、代码、测试之间的追溯关系

每个开发任务都应能回溯到需求和设计，每个测试用例都应能回溯到验收标准。

推荐建立如下追溯关系：

```text
需求 → 设计 → 任务 → 代码 → 测试 → 验收
```

## 2. 分工原则

| 参与方 | 主要职责 |
| --- | --- |
| 开发人员 | 提供背景、边界、关键约束、确认待决问题、判断验收是否通过 |
| AI | 阅读规范和代码、生成 spec、识别缺口、拆解任务、实现代码、回填文档 |

开发人员不需要一开始就写完整 `requirements.md`、`design.md`、`tasks.md`。更推荐先把原始材料交给 AI, 让 AI 生成第一版, 再由开发人员确认。

## 3. 推荐协作流程

### 3.1 输入原始材料

可以直接给 AI 产品想法、会议纪要、截图、接口文档、历史代码路径或口头描述。

推荐提示:

```text
请按 docs/spec-coding-guide/SPEC_CODING_GUIDE.md 协助我推进这个需求。

需求背景:
- xxx

已有材料:
- xxx

我的初步边界:
- 本期做:
- 本期不做:
- 待确认:

请先完成:
1. 判断是否需要 spec
2. 生成或更新 docs/specs/<feature-name>/ 下的 requirements/design/tasks
3. 标出需要我确认的问题
4. 在我确认前不要写代码
```

### 3.2 先澄清, 再编码

当需求不清楚时, 要求 AI 先输出理解和问题, 不要直接进入实现。

推荐提示:

```text
先不要写代码。请基于现有材料整理:
1. 需求理解
2. 本期范围
3. 不做范围
4. 待确认问题
5. 建议的 spec 目录和文档
```

### 3.3 人工确认关键决策

开发人员重点确认以下内容:

- 本期到底做什么
- 本期明确不做什么
- AI 是否脑补了未确认需求
- 验收标准是否能判断成败
- 技术方案是否符合当前工程实现
- 哪些问题必须现在拍板

确认时不需要长篇改文档, 可以直接给决策:

```text
本期只做 A/B, 不做 C。
自动触发先不做, 放后续。
验收以 CUI 可见通知为准。
按这个更新 spec。
```

### 3.4 确认后再实现

当范围和设计确认后, 再让 AI 拆任务并编码。

推荐提示:

```text
确认以上范围。请按 spec 拆 tasks 并开始实现。
实现时每个改动都要能回溯到 requirements/design/tasks。
完成后回填 tasks 和验证结果。
```

### 3.5 变更先归类

开发过程中出现新发现时, 不要直接让 AI 顺手实现。先要求 AI 分类:

```text
这个新发现属于本期必须做、架构必要约束、待确认问题, 还是后续演进?
请先更新 spec, 再说明是否建议进入本期实现。
```

只有明确属于本期范围或架构必要约束的内容, 才进入当前实现。

### 3.6 收尾回填

实现完成后, 让 AI 对齐文档和代码:

```text
根据实际实现回填 tasks 和验证结果。
如果 spec 和代码实现不一致, 以代码为准指出差异, 并更新 spec。
```

## 4. 开发人员检查清单

进入编码前, 至少确认:

- [ ] AI 已阅读 `docs/spec-coding-guide/SPEC_CODING_GUIDE.md`
- [ ] 需求已有明确的本期范围和不做范围
- [ ] 待确认问题已由人工回答, 或明确标为后续
- [ ] 设计没有超出需求范围
- [ ] tasks 能对应到需求和设计
- [ ] 验收标准能判断成功或失败

实现完成后, 至少确认:

- [ ] tasks 状态已回填
- [ ] 验证命令或人工验收结果已记录
- [ ] spec 与实际代码没有明显冲突
- [ ] 新发现已分类为本期、待确认或后续演进

## 5. 常用提示

判断是否需要 spec:

```text
请按 Spec Coding 规范判断这个需求是否需要建 spec。
如果不需要, 请说明原因并给出最小实现和验证计划。
```

生成第一版 spec:

```text
请基于这些材料生成 docs/specs/<feature-name>/ 的第一版 spec。
至少包含 README.md、requirements.md、design.md、tasks.md。
不确定内容必须标为待确认, 不要写成已确认结论。
```

审查已有 spec:

```text
请按产品、架构、开发负责人、QA、Reviewer 角色审查这个 spec。
指出阻塞问题、范围漂移、待确认问题和建议调整点。
```

按代码对齐 spec:

```text
请对照当前代码实现检查 spec 是否过时。
如果文档和代码冲突, 以实际实现为准, 更新 spec 并说明调整点。
```

进入实现:

```text
范围已确认。请按 tasks 开始实现, 并在完成后回填任务状态和验证结果。
```

## 6. 常见误区

- 不要把 spec 当成开发人员手写文档任务; 它是 AI 和人协作的契约。
- 不要让 AI 在需求未确认时直接编码。
- 不要把 AI 的合理猜测直接当成已确认需求。
- 不要让 references 替代主文档; 主文档必须摘出可执行结论。
- 不要实现所有“看起来顺手”的优化; 先判断是否属于本期。

## 7. 一句话工作法

```text
开发人员负责目标、边界、决策和验收判断; AI 负责整理、生成、实现和回填。
```
