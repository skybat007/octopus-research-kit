# Spec Coding 使用规范

本文档用于指导 Codex / Code Agent 在本项目中正确使用 Spec 文档进行需求分析、技术设计、任务拆解、测试设计和代码实现。

Spec Coding 的核心目标不是“多写文档”，而是让需求、设计、任务、代码、测试之间建立清晰的可追溯关系，避免 Code Agent 在需求不清、边界不明、设计未确认的情况下直接生成代码。

本文只定义 Spec Coding 范式。它不替代具体工程对象的开发范式，例如 OpenClaw Skill 范式、前端工程规范、后端服务规范、发布手册或打包流程。

当一个需求的实现对象是某类专项工程时，应先用本文判断“需求是否足够支撑编码”，再按对应工程范式完成实现、验证和发布检查。

---

## 0. 快速使用

可以先按轻量流程使用，不要求所有需求一次性补齐全套文档。

1. 判断任务是否需要 spec：
   - 简单小修、小型配置修正、明确 bug 修复：不单独建 spec。
   - 新功能、复杂改造、接口/数据/状态/权限/异步任务、多模块联调、不完整产品材料：先建 spec。
2. 在 `docs/specs/<feature-name>/` 下建目录。
3. 优先使用 `docs/spec-coding-guide/templates/` 中的模板，至少准备：
   - `requirements.md`
   - `design.md`
   - `tasks.md`
4. 复杂需求进入 Coding 前做 Coding Readiness Check。
5. 实现完成后回填 `tasks.md` 的状态和验证结果。
6. 已完成且不再维护的 spec，按归档规则移入 `docs/specs-archive/<year>/`。

## 1. 基本原则

### 1.1 先 Spec，后 Coding

当用户提出以下类型任务时，必须优先检查或生成 Spec：

- 新功能开发
- 复杂功能改造
- 多系统联调
- 涉及接口、数据库、状态流转、权限、异步任务的开发
- 涉及多个模块或多个服务的改动
- 用户只提供了产品想法、会议纪要、技术设想、截图或不完整需求

简单小修、小型配置修正、明确 bug 修复可以不单独建立完整 Spec，但仍应确认改动范围和验证方式。

除非用户明确要求“先不要写文档，直接改代码”，复杂任务不得直接进入编码。

---

### 1.2 Spec 是开发依据，不是装饰文档

Spec 文档必须能够回答以下问题：

- 为什么要做？
- 给谁用？
- 本期做什么？
- 本期不做什么？
- 主流程是什么？
- 异常流程是什么？
- 涉及哪些系统和模块？
- 接口和数据如何流转？
- 如何验收？
- 开发任务如何拆解？
- 代码实现是否能回溯到需求？

如果 Spec 无法回答这些问题，应先补充或标记待确认，而不是直接编码。

---

### 1.3 新增发现必须分类，不得直接进入本期实现

Code Agent 可以在需求分析、技术设计、任务拆解和测试设计过程中主动发现潜在需求、隐含约束、非功能性要求和后续演进方向。

但不得因为“合理”“常见”“最佳实践”而将未确认内容直接写成本期确定要实现的范围，更不得在 Coding 阶段直接实现未被 Spec 确认的功能。

所有新增发现必须按以下类型归类：

1. 已确认范围：原始需求明确提出，或用户已经确认。
2. 建议纳入本期：为完成主流程闭环有明显价值，但仍需用户确认。
3. 架构必要约束：为保证正确性、安全性、幂等性、可观测性等所必需的技术约束。
4. 待确认问题：当前材料不足，不能直接定稿。
5. 后续演进：有价值但不影响本期最小闭环。
6. 不做范围：明确本期不实现的内容。

除“已确认范围”和经过说明的“架构必要约束”外，其他内容不得直接进入 Coding 范围。

---

### 1.4 推测必须显式标记

如果原始材料中没有明确说明，Code Agent 可以提出合理假设，但必须标记为：

```text
待确认：
```

或：

```text
本期暂定：
```

不得把推测内容写成确定结论。

错误示例：

```text
系统默认安装最新版本 Skill。
```

正确示例：

```text
待确认：安装时是否默认选择最新版本 Skill。
本期暂定：由能力集市返回可安装 Skill 信息，主智伴不做版本新旧判断。
```

## 2. 推荐目录结构

如果项目已经有自己的 spec 目录约定，应优先沿用项目现状。

例如 `supply-capacity-poc` 这类项目推荐使用：

```text
docs/spec-coding-guide/
  README.md
  SPEC_CODING_GUIDE.md
  GLOSSARY.md
  roles/
    product-manager.md
    architect.md
    tech-lead.md
    qa.md
    reviewer.md
  templates/
    requirements-template.md
    design-template.md
    tasks-template.md
    acceptance-template.md
    test-cases-template.md
    spec-review-template.md

docs/specs/
  <feature-or-skill-name>/
    README.md
    requirements.md
    design.md
    tasks.md
    acceptance.md        # 可选，复杂需求建议独立
    api-design.md        # 可选，涉及接口时使用
    data-design.md       # 可选，涉及数据结构/状态/持久化时使用
    test-cases.md        # 可选，复杂验收或回归要求较高时使用
    spec-review.md       # 可选，复杂需求进入 Coding 前使用
    references/          # 可选，原始资料、外部契约、可复用说明或调研材料

docs/specs-archive/
  <year>/
    <archived-feature-name>/
```

其中 `docs/spec-coding-guide/` 是规范辅助目录，不代表具体业务 spec；`docs/specs/` 只放具体业务、能力或专项需求 spec。
已完成且不再作为当前契约维护的历史 spec 放入 `docs/specs-archive/<year>/`。
`references/` 用于存放支撑 spec 的参考材料，不应替代 `requirements.md`、`design.md`、`tasks.md` 等主文档；主文档必须摘出可执行结论，不能只要求读者自行理解 references。

简单需求可以合并文档，但至少应能表达：

```text
需求目标
本期范围 / 不做范围
主要设计或改动点
任务拆分
验收或验证方式
```

## 2.1 Spec 生命周期与归档

每个长期维护的 spec 建议在 `README.md` 开头声明：

```text
Status: active | maintained | shipped | archived | superseded
Owner: <owner>
Last Updated: YYYY-MM-DD
```

状态说明：

- `active`：正在设计、开发或联调。
- `maintained`：已上线，但仍作为当前开发、联调或验收契约维护。
- `shipped`：已完成，短期没有继续迭代计划，可准备归档。
- `archived`：已移入 `docs/specs-archive/<year>/`，仅保留历史参考。
- `superseded`：已被新的 spec 替代，应注明替代 spec。

归档规则：

- `docs/specs/` 只保留当前仍有参考价值的工作中或维护中 spec。
- 已完成且不再作为当前契约维护的 spec，移入 `docs/specs-archive/<year>/`。
- 被新 spec 替代的旧 spec，移入 archive 前应在 `README.md` 标注 `Status: superseded` 和替代路径。
- 不要把 spec 归档到 `output/`；`output/` 只放运行产物。

## 3. 范围分类规则

Code Agent 在分析过程中发现任何新增内容时，必须先分类，再决定是否进入本期实现。

### A. 已确认范围

满足以下任一条件：

- 用户明确提出
- 产品文档明确写明
- 已在 `requirements.md` 中确认
- 已被验收标准覆盖

可以进入本期实现。

### B. 架构必要约束

虽然产品文档没有直接提出，但为了保证系统正确性、安全性或可维护性必须具备。

例如：

- 幂等
- 权限校验
- 参数校验
- 错误码
- 日志
- 超时控制
- 基础异常处理
- 数据一致性保护

可以进入技术设计，但必须说明原因。

### C. 建议纳入本期

对本期体验或闭环有明显价值，但不是原始需求明确提出。

必须标记为“建议纳入本期”，等待确认。

### D. 待确认问题

材料不足，无法判断是否应该实现。

不得进入 Coding。

### E. 后续演进

有价值，但不影响本期最小闭环。

不得进入本期 Coding。

### F. 不做范围

明确本期不实现。

不得设计、不得拆任务、不得编码。

## 4. 文档职责边界

### 4.1 `requirements.md`

需求文档由产品视角输出，关注“做什么”和“为什么做”。

必须包含：

- 背景
- 目标
- 用户角色
- 使用场景
- 功能范围
- 不做范围
- 主流程
- 异常流程
- 业务规则
- 待确认问题

不得包含：

- 数据库表结构
- 具体类名、方法名
- 过细的代码实现方案
- 未确认的技术假设

---

### 4.2 `acceptance.md`

验收文档关注“怎么证明做完了”。

必须包含：

- 功能验收标准
- 业务验收标准
- 异常场景验收
- 权限验收
- 数据一致性验收
- 可观测性验收
- 人工验收点
- 自动化测试建议

每一条验收标准都应尽量可验证。

---

### 4.3 `design.md`

技术设计文档由架构师视角输出，关注“系统怎么实现”。

必须包含：

- 系统参与者
- 模块边界
- 调用链路
- 时序图
- 状态流转
- 异常处理
- 幂等策略
- 权限校验
- 日志与监控
- 技术风险
- 扩展点

不得做以下事情：

- 改变需求范围
- 引入需求中没有的新业务系统
- 把后续演进内容混入本期设计
- 为了“架构完整”而过度设计

---

### 4.4 `api-design.md`

接口设计文档关注服务之间如何交互。

必须包含：

- 接口名称
- 请求方
- 提供方
- 请求参数
- 响应参数
- 错误码
- 幂等字段
- 鉴权方式
- 超时策略
- 重试策略
- 示例请求
- 示例响应

接口必须能回溯到 `requirements.md` 或 `design.md`。

---

### 4.5 `data-design.md`

数据设计文档关注数据结构、状态和持久化。

必须包含：

- 核心对象
- 字段说明
- 状态枚举
- 状态流转
- 数据来源
- 数据写入方
- 数据读取方
- 数据一致性要求

不得在没有需求支撑的情况下新增复杂数据模型。

---

### 4.6 `tasks.md`

任务文档由开发负责人视角输出，关注“怎么拆、怎么做、先做什么”。

必须包含：

- 任务编号
- 任务名称
- 对应需求编号
- 对应设计章节
- 优先级
- 前置依赖
- 主要改动点
- 验收方式
- 是否可 Mock
- 是否需要联调

任务拆解必须围绕最小闭环，不得机械地按 Controller / Service / DAO 拆成无业务意义的任务。

---

### 4.7 `test-cases.md`

测试文档由测试负责人视角输出，关注“怎么测”。

必须包含：

- 正常流程测试
- 异常流程测试
- 权限测试
- 幂等测试
- 超时测试
- 数据一致性测试
- 回归测试范围
- 人工验收检查项

测试用例必须能映射到验收标准。

---

### 4.8 `GLOSSARY.md` / `glossary.md`

术语表用于统一业务和技术概念。

仓库级通用术语放在 `docs/spec-coding-guide/GLOSSARY.md`；单个需求的专项术语也可以放在对应 spec 目录下的 `glossary.md`。

必须包含：

- 术语名称
- 术语定义
- 相关系统
- 不应混淆的概念
- 示例

---

### 4.9 `assumptions.md`

假设文档用于记录当前还没有确认但为了推进设计临时采用的前提。

假设建议跟随具体需求维护：简单需求可以写在 `requirements.md` 的“待确认问题 / 本期暂定”章节；复杂需求也可以放在对应 spec 目录下的 `assumptions.md`。

必须包含：

- 假设内容
- 影响范围
- 风险
- 需要谁确认
- 确认状态
- 如果假设不成立的替代方案

---

### 4.10 `spec-review.md`

审查文档用于检查 Spec 的一致性。

必须检查：

- 需求是否清楚
- 不做范围是否明确
- 设计是否超出需求
- 任务是否能映射到需求
- 测试是否覆盖验收标准
- 是否存在未标记的假设
- 是否存在过度设计
- 是否存在术语不一致
- 是否存在参与者错误
- 是否存在接口、状态、数据不一致

---

## 5. 角色化产出规范

生成不同类型文档时，应采用不同角色视角，但角色定义必须轻量，不得过度扮演。

### 5.1 产品经理角色

适用文档：

- `requirements.md`
- `acceptance.md`
- `GLOSSARY.md` / `glossary.md`

职责：

- 梳理用户、场景、目标和业务流程
- 明确本期范围和不做范围
- 输出功能需求和验收标准
- 标记待确认问题

边界：

- 不设计数据库表
- 不指定代码实现
- 不擅自把未确认需求写入已确认范围
- 不把技术推测写成产品结论

---

### 5.2 架构师角色

适用文档：

- `design.md`
- `api-design.md`
- `data-design.md`

职责：

- 识别系统参与者和服务边界
- 设计主流程、异常流程和状态流转
- 定义接口、数据、权限和幂等策略
- 识别风险和扩展点
- 补充必要的非功能性约束

边界：

- 不改变需求范围
- 不引入无需求支撑的新业务流程
- 不做超出本期范围的复杂设计
- 所有设计必须能回溯到需求或验收标准

---

### 5.3 开发负责人角色

适用文档：

- `tasks.md`
- `milestone.md`
- `integration-plan.md`

职责：

- 按最小闭环拆任务
- 标注优先级、依赖、联调顺序
- 区分必须开发、可 Mock、后续优化
- 保证每个任务可执行、可验证

边界：

- 不新增需求
- 不改变技术设计
- 不把后续演进混入本期任务
- 不拆无业务价值的空泛任务

---

### 5.4 测试负责人角色

适用文档：

- `test-cases.md`
- `acceptance-checklist.md`

职责：

- 设计测试场景
- 覆盖正常、异常、权限、幂等、超时、数据一致性
- 标记人工验收点和自动化测试点

边界：

- 不改变验收标准
- 不扩大功能范围
- 不假设不存在的页面或接口

---

### 5.5 Spec 审查者角色

适用文档：

- `spec-review.md`

职责：

- 检查需求、设计、任务、测试的一致性
- 识别过度设计
- 识别未确认假设
- 识别任务与需求不匹配
- 输出修改建议

边界：

- 不直接新增需求
- 不直接改变设计
- 不直接进入编码
- 只输出问题、风险和建议

---

## 6. 推荐执行流程

```text
原始材料
  ↓
需求澄清
  ↓
生成 requirements.md / acceptance.md / GLOSSARY.md 或 glossary.md
  ↓
生成 design.md / api-design.md / data-design.md
  ↓
生成 tasks.md
  ↓
生成 test-cases.md
  ↓
生成 spec-review.md
  ↓
修正 Spec
  ↓
进入 Coding
  ↓
执行测试
  ↓
回填文档
```

## 7. 需求编号与可追溯规则

所有需求、设计、任务、测试必须有编号。

推荐编号方式：

```text
REQ-001：需求
AC-001：验收标准
DES-001：设计项
API-001：接口
DATA-001：数据项
TASK-001：开发任务
TC-001：测试用例
RISK-001：风险
Q-001：待确认问题
```

映射关系示例：

```text
TASK-003：实现 Skill 安装请求接口

关联：
- REQ-004：用户点击安装 Skill
- DES-006：安装请求链路
- API-002：创建安装任务接口
- AC-003：安装受理成功后返回结果
- TC-005：安装成功流程测试
```

任何无法建立映射关系的任务，都应重新审查是否必要。

## 8. Coding 阶段规则

### 8.1 编码前必须读取

编码前必须读取当前需求目录下的：

```text
requirements.md
design.md
tasks.md
验收标准
```

验收标准可以独立放在 `acceptance.md`，也可以作为 `requirements.md` 或 `tasks.md` 的章节存在。

如果涉及接口，必须读取：

```text
api-design.md 或 design.md 中的接口设计章节
```

如果涉及数据结构，必须读取：

```text
data-design.md 或 design.md 中的数据设计章节
```

如果涉及测试，必须读取：

```text
test-cases.md 或 tasks.md 中的验证计划
```

---

### 8.2 只实现当前任务范围

Code Agent 只能实现当前任务对应的需求和设计。

不得顺手做以下事情：

- 大范围重构
- 修改无关模块
- 新增未要求功能
- 改变已有接口语义
- 新增生产依赖
- 修改数据库结构
- 删除已有逻辑
- 改变权限模型

除非当前任务明确要求。

---

### 8.3 发现 Spec 问题时的处理方式

如果编码过程中发现 Spec 不完整、矛盾或不可实现，不得自行决定实现方式。

应输出：

```text
发现 Spec 问题：

问题：
影响：
建议：
需要确认：
```

然后等待用户或维护者确认。

---

### 8.4 实现完成后必须回填

代码实现完成后，应检查是否需要更新：

- `tasks.md` 的任务状态
- `acceptance.md` 的验收状态
- `api-design.md` 的接口变更
- `data-design.md` 的字段变更
- `test-cases.md` 的测试结果
- `spec-review.md` 的遗留问题

## 9. Coding Readiness Check

Coding Readiness Check 用于判断“当前 Spec 是否足够支撑编码”。它是开工前检查，不是审批流程，也不是具体工程对象的质量检查。

### 9.1 分级规则

#### 小修小补

例如错别字、注释、明确的一行配置、确定性 bug 修复。

可以不显式输出检查表，但 Code Agent 仍应在动手前确认：

- 改动范围明确
- 不涉及额外需求
- 验证方式明确

#### 普通功能或改造

可以使用轻量检查：

```text
Coding Readiness Check:
- 本期要做什么：明确
- 本期不做什么：明确
- 主要改动点：明确
- 验证方式：明确
- 阻塞问题：无
结论：可以开始编码
```

#### 复杂需求

涉及跨模块、多系统联调、接口、数据结构、状态流转、权限、异步任务、重要写操作或多人协作时，必须显式检查：

```text
[ ] requirements.md 已存在并可用
[ ] design.md 已存在并可用
[ ] tasks.md 已存在并可用
[ ] 验收标准已存在并可用
[ ] 当前任务已在 tasks.md 中定义
[ ] 当前任务能映射到需求
[ ] 当前任务能映射到设计
[ ] 当前任务有验收方式
[ ] 不存在阻塞级待确认问题
[ ] 不涉及未授权的范围扩展

结论：
- 可以进入 Coding
- 暂不建议进入 Coding，原因是：
```

只有在结论为“可以进入 Coding”时，才开始修改代码。

### 9.2 与工程质量检查的关系

Coding Readiness Check 只检查 Spec 是否足够支撑编码。

如果当前实现对象是 OpenClaw Skill、前端页面、后端服务、数据脚本或其他专项工程，还应在实现或发布阶段执行对应工程范式要求的检查。

例如 OpenClaw Skill 的执行模式、运行态上下文、结构化输出、敏感信息脱敏、打包发布等，属于 Skill 工程质量检查，不属于 Coding Readiness Check 本身。

## 10. 总结

Spec Coding 的目标是：

```text
用 Spec 约束 Agent，
用需求约束设计，
用设计约束任务，
用任务约束代码，
用验收标准约束完成质量。
```

Code Agent 必须把 Spec 当作开发契约，而不是参考材料。

当 Spec 不清楚时，优先澄清 Spec。
当设计和需求冲突时，优先回到需求。
当任务和设计冲突时，优先回到设计。
当代码实现超出任务时，必须停止并说明原因。
